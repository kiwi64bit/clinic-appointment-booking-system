Software Requirements Specification (SRS)

Project: Clinic Appointment Booking System · Course: System Analysis and Design 1 (Project 3) · Version: 1.1

Web-based scheduling specification covering patient booking, doctor schedules, clinic administration, domain rules, and front-end pages.

1. Purpose & Scope

The Clinic Appointment Booking System is a web-based scheduling application that lets patients find doctors, check open time slots, and book, reschedule, or cancel clinic visits. Doctors use it to check their daily schedule, manage their time slots, and record whether patients attended or missed visits, while administrators manage medical specialties, doctor profiles, time slots, patient records, and clinic appointments.

For this System Analysis and Design 1 course project, the system is built as a front-end web application using browser storage (such as localStorage or a structured JSON store in memory) seeded with sample data instead of a live backend database server.

4. Detailed Functional Requirements

Each subsection below gives the complete plain-text behavior for one requirement so diagram authors and developers share the exact same rules.

FR-01 — Patient Registration

A visitor who does not yet have an account can open the registration form and submit their full name, email address, phone number, date of birth, and password. The system checks that all required fields are filled in and that the email format is valid. It then checks existing patient records to make sure no other account already uses that email address. If the email is already registered, the system rejects the sign-up and shows a clear error message without creating a duplicate account. If the input is valid and the email is unique, the system creates a new Patient record with role Patient, stores the password safely (hashed rather than plain text), saves it to storage, and lets the user sign in.

FR-02 — Role-Based Login

Any registered user—whether a Patient, Doctor, or Administrator—can enter their email and password on the Login Page. The system checks the submitted credentials against stored user accounts. If the email is not found or the password does not match, the system denies access and displays an invalid login message. When the credentials match, the system starts an active session for that user and redirects them to their role's home view: the Patient Dashboard for patients, the Doctor Dashboard for doctors, or the Admin Dashboard for administrators.

FR-03 — Browse Doctors & View Profile

A logged-in patient can open the Doctors List view to see doctors who are active in the clinic. By default, doctors marked as inactive are hidden from new patient browsing. The patient can filter the list by choosing a Specialty or typing a search term to match a doctor's name. The system updates the displayed list right away and shows a friendly message if no active doctors match the selected filter or search text. When the patient selects a doctor from the list or search results, the system opens the Doctor Profile view for that doctor. It displays the doctor's full name, assigned Specialty, years of experience, consultation fee, short biography, and consultation hours or working days. From this profile, the patient can jump directly into checking available dates and time slots for that doctor.

FR-04 — View Available Time Slots

On the Doctor Profile or Appointment Booking view, a patient picks a doctor and a calendar date. The system looks up all TimeSlot entries for that doctor on that date and displays each slot's start and end time along with its status (Available, Booked, or Blocked). Only slots with status Available (and in the future) can be selected for booking; Booked and Blocked slots are visibly marked as unavailable so the patient cannot pick them.

FR-05 — Book Appointment

After selecting an Available TimeSlot for a doctor and date, the patient reviews the booking summary and clicks confirm. Before saving, the system runs the conflict checks defined in FR-06. If no conflict exists, the system creates a new Appointment linked to the patient, doctor, and chosen TimeSlot with status Booked, changes the TimeSlot status from Available to Booked, saves both changes to storage, and shows a booking confirmation message.

FR-06 — Conflict & Double-Booking Prevention

Whenever a booking or reschedule is submitted, the system must check two things before saving: first, that the target TimeSlot still exists, belongs to the chosen doctor, and still has status Available; second, that the same patient does not already have another active Booked appointment on the same date and overlapping time. If either check fails, the system cancels the save operation, keeps existing records unchanged, and shows a clear error message telling the patient why the slot cannot be booked and prompting them to choose another slot.

FR-07 — View Patient Appointments

A logged-in patient can open My Appointments to view all appointments they have made. The appointments are separated or filterable into Upcoming and Past visits. Each entry shows the doctor's name, specialty, appointment date, time slot, and current status (such as Booked, Completed, Cancelled, or No-Show) so the patient can easily track what is ahead and what has already happened.

FR-08 — Cancel Appointment

From My Appointments, a patient can choose to cancel an appointment that is currently in Booked status and scheduled for the future. The system asks for confirmation (and enforces any cutoff rule if defined in the team's business rules), updates the Appointment status to Cancelled, and sets the linked TimeSlot status back to Available so another patient can book it. Past, completed, cancelled, or no-show appointments cannot be cancelled by the patient.

FR-09 — Reschedule Appointment

A patient with an upcoming Booked appointment can choose to reschedule it to another Available TimeSlot. The patient picks a new date and an open slot, and the system checks for conflicts on the new slot (FR-06) before making any change. If the new slot is free and valid, the system updates the Appointment to point to the new TimeSlot (keeping status Booked), marks the new slot as Booked, and returns the old TimeSlot to Available. If the new slot is not available, the system blocks the change and keeps the patient's original appointment intact.

FR-10 — View Doctor Daily Schedule

When a doctor opens the Doctor Dashboard, the system shows the appointments assigned to that doctor for today or for a date the doctor selects. The list is sorted in chronological order by start time and shows each appointment's time window, patient name, basic visit notes or reason, and current status. Only appointments belonging to the logged-in doctor are shown.

FR-11 — Update Appointment Visit Status

On the Doctor Dashboard, a doctor can update the status of a scheduled appointment from Booked to either Completed (when the visit took place) or No-Show (when the patient did not attend). The system saves the updated status immediately so it appears in the doctor's schedule, the patient's past appointments list, and administrator reports. Once marked Completed or No-Show, the visit is treated as finished rather than an open upcoming booking.

FR-12 — Manage Specialties

An administrator working in the Admin Dashboard can create a new medical Specialty (such as Cardiology or Dermatology) by entering a specialty name and optional description, or edit the name and description of an existing specialty. The system validates that the specialty name is not blank or duplicated and updates the list immediately so patients and administrators see the current specialties.

FR-13 — Manage Doctor Profiles

An administrator can add a new Doctor account with profile details (name, email, specialty, experience years, consultation fee, and bio) or edit an existing doctor's profile information and assigned specialty. An administrator can also deactivate a doctor (or set them as inactive). Deactivating a doctor stops patients from seeing them as available for new bookings while keeping their past appointments and history intact.

FR-14 — Manage Doctor Time Slots

A doctor (for their own schedule) or an administrator (for any doctor) can create new TimeSlot entries for a chosen date and time range, or mark an unbooked Available slot as Blocked when a doctor is unavailable or the clinic has a closure. The system prevents overlapping slots for the same doctor and does not allow blocking a slot that already has an active Booked appointment without first handling that appointment.

FR-15 — Admin Appointment Oversight

An administrator can view all appointments across the clinic and filter them by date, doctor, patient, or status (Booked, Cancelled, Completed, No-Show). If a doctor becomes unavailable or an administrative change is required, the administrator can cancel a Booked appointment, which updates the appointment status to Cancelled and releases its TimeSlot back to Available.

FR-16 — View & Search Patient Records

An administrator can view a list of registered Patient accounts and search or filter them by name, email, or phone number. Selecting a patient lets the administrator view their contact details and inspect their appointment history so clinic staff can answer questions or assist with scheduling issues.

6. Detailed Non-Functional Requirements

NFR-01 — Usability & Feedback

Every action a user takes—such as registering, logging in, booking a slot, cancelling or rescheduling an appointment, updating a visit status, or saving admin changes—must produce visible feedback on screen right away (within 1 second). Validation errors must point out missing or invalid inputs clearly, and conflict alerts must explain why a slot could not be taken.

NFR-02 — Responsive Design

All front-end pages must adapt smoothly to both desktop screens (1024px wide and above) and mobile screens (375px wide and above). Navigation menus, tables, slot grids, and forms should stack or scroll cleanly inside their containers without breaking page layout or forcing horizontal scrolling across the whole page.

NFR-03 — Data Integrity & Persistence

When the app starts for the first time, it loads clean sample seed data (specialties, doctors, time slots, patients, and appointments) into browser storage (such as localStorage). Any new registration, booking, cancellation, reschedule, status update, or admin change updates that stored data so changes stay intact across page refreshes until reset.

NFR-04 — Access Control & Naming Consistency

Users who are not logged in must be sent to the Login Page rather than accessing role dashboards directly, and a logged-in user must only see and perform actions allowed for their role. In addition, class names, slot/appointment statuses, and page names must stay identical across this SRS, all SAD 1 diagrams, and the front-end code so the team avoids confusion.

7. Domain Rules & Data States

TimeSlot Statuses

  • Available: Open and eligible to be booked.
  • Booked: Reserved by an active (Booked) appointment.
  • Blocked: Unavailable due to clinic closure, doctor leave, or manual blocking.

Appointment Statuses

  • Booked: Active confirmed appointment.
  • Cancelled: Cancelled by the patient or administrator; releases the associated TimeSlot to Available if still in the future.
  • Completed: Visit completed as recorded by the doctor.
  • No-Show: Patient missed the scheduled appointment as recorded by the doctor.

Core Domain Classes & Business Rules

  • Core classes: Patient, Doctor, Specialty, Appointment, TimeSlot, and Administrator (plus User if modeling shared login/profile attributes).
  • A TimeSlot can hold at most one active (Booked) Appointment at any time.
  • A Patient cannot hold two overlapping Booked appointments on the same date and start time.
  • Rescheduling checks the target slot first so an existing booking is not lost if a conflict occurs.
  • Deactivating a Doctor prevents new bookings while keeping existing historical records intact.
